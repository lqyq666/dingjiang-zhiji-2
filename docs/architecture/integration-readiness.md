# 集成与同步清单：这份代码逐条对得上什么

一份常见的"跨系统同步/集成"问题清单共 32 条，大多来自 金蝶 → WPS 双写场景。
这份文档把它逐条对照到本仓库：**已经具备的**指出落点和证据，**本轮补上的**说明为什么原来不够，**不适用的**说明边界在哪。

判断标准只有一条：能在代码或数据库里指出来才算具备，口径不算。

## 二、本轮补上的（5 条，`7eb2ebd`）

外发通知链路（`apps/api/src/integration/feishu-work.notifier.ts`）原来只做到"崩溃能恢复"，没有"失败能结束"。补的五条都在这条链路上：

| #        | 问题                               | 原来怎样                                                                     | 现在怎样                                                                                             |
| -------- | ---------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 3        | 凭证过期返回 401                   | 缓存 token 一次性使用，过期后整条通知直接失败，等下一轮重试                  | 命中鉴权错误时作废缓存、重取 token、在同一次尝试内重试一次                                           |
| 10       | 部分成功/状态未知                  | 无尝试上限，`attempts` 只增不看                                              | 失败按指数退避排期，`next_attempt_at` 到期才可认领                                                   |
| 11       | 死信队列                           | 永久性失败（未绑定、机器人被停用）每轮扫描都重试，永不停止                   | 尝试预算耗尽转 `DEAD` + `dead_at`，不再进入认领范围                                                  |
| 21       | 限流 429                           | 把 429 当普通失败，立刻重试                                                  | 读 `Retry-After`，落成持久化退避；到期前该行不可认领                                                 |
| 24/25/26 | Token 并发刷新 / 锁过期 / 栅栏令牌 | 10 个并发投递会发 10 次 token 请求；租约过期被接管后，旧 worker 仍能写回结果 | token 请求单飞（共享同一个 Promise）；`settle` 以 `attempts=$n` 为栅栏，过期 worker 的写入匹配不到行 |

验证方式：10 个单元用例钉住查询形状，5 个真实 PostgreSQL 用例钉住形状表达不了的语义（退避未到期不可认领、卡在 `FAILED` 且预算耗尽不再触达飞书、租约被接管保留新结果）。两处关键判据做过变异：去掉预算判据 → 1 条红；去掉栅栏 → 1 条红；其余全绿。

## 三、不适用（16 条）

| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 业务需求与指标口径属于产品定义，不在代码仓库范围                                                                                                                                                                                                    |
| 2   | 本仓库没有金蝶/WPS 双写服务。`intake` 处理的是 CSV 与人工上传（`production_source_files` + sha256），没有外部 ERP API 客户端                                                                                                                        |
| 4   | 同上：没有 Extract-Transform-Load 到外部系统的链路。仓库内确实有"字段映射 + 类型转换 + 唯一约束隔离异常"，但目标是自己的 PostgreSQL，不是 WPS                                                                                                       |
| 5   | 没有分页读取外部接口的场景。数据入口是整文件导入，批次记录在 `production_source_files.row_count`                                                                                                                                                    |
| 6   | 没有增量同步。导入以文件为单位、幂等 upsert，不做 `updated_at` 增量拉取                                                                                                                                                                             |

| 13  | 没有"外部系统状态变更多端同步"。取消/撤回在本系统内以 `status='WITHDRAWN'` + `withdrawn_at` 软删除表达，逻辑已在域内闭环                                                                                                                            |

## 四、如果真要做金蝶 → WPS 同步，缺的是什么

按这份清单的顺序，最小可信实现需要（当前仓库**没有**）：

1. 一个 `services/erp-sync` 进程：分页读取、`(updated_at, detail_id)` 复合游标、检查点表；
2. 一个适配层把两个平台的字段与授权差异收在一处，业务代码只见统一模型；
3. 一个对账任务：比唯一 ID 集合与金额汇总，不一致写差异表；
4. 一个 Redis 或 PostgreSQL 版的全局限流器（单机用 PostgreSQL advisory lock 就够，不必上 Redis）。

这四件事都属于"新增子系统"，不是"优化现有代码"，所以没有塞进这一轮。

## 五、这份对照能证明什么

- 清单里的"经典问题"在这个项目里**不是靠自觉解决的，而是靠可执行的门**：审计篡改、幂等重放、并发同键、退避未到期，每一条都有会失败的用例。
- 判断哪些该做、哪些不该做，标准是"能不能指出落点"。指不出落点的，就不写代码，写清楚边界。
